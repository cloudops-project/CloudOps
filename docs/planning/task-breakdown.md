# Initial Backlog and Task Board

## Purpose and audience

The project lead and team use this template to turn approved phases into linked, reviewable GitHub issues.

## Stage 0 epics

- Product approval: review PRD, scope, personas, success measures, assumptions, and glossary.
- Architecture approval: system/components/data flow, onboarding, tenancy, database/API, threat/failure/trust design, and ADR decisions.
- Experience approval: information architecture, design tokens, wireframes, flows, accessibility, and responsive policy.
- Engineering approval: development/API/database/security/AI/rule/error/log/test/DoD standards.
- Delivery governance: phases, roadmap, responsibilities, risks, memory, operations plans, Git settings, templates, and board.

## Board and issue format

Use Backlog → Ready → In Progress → In Review → Testing → Blocked → Done. An issue includes problem/outcome, scope/exclusions, acceptance criteria, dependencies, security/tenant impact, owner/reviewer, test/documentation needs, demo evidence, and open questions. Ready means dependencies and acceptance criteria are clear; Blocked records cause, owner, and next check.

## Suggested labels

Areas: `area:backend`, `area:frontend`, `area:aws`, `area:security`, `area:devops`, `area:documentation`. Types: `type:feature`, `type:bug`, `type:research`, `type:security`. Priority: `priority:critical`, `priority:high`, `priority:medium`, `priority:low`. Flow: `status:blocked`. Add `stage:N` and `needs:decision` only if the team agrees.

## Milestones and open questions

Use milestones aligned to approved stages or demonstrable release gates, not arbitrary dates. Approve work-in-progress limits, estimation method, definition of Ready, triage cadence, label colors, and who moves cards after review/testing.
